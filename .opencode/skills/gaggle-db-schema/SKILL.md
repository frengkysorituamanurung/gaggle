# Skill: Gaggle DB Schema & SQLite Conventions

Follow these rules whenever working inside `crates/gaggle-db` or adding new tables, columns, indexes, or queries.

## 1. Mandatory Column & Data Type Conventions
- **Primary Keys**: Always `TEXT` containing a time-ordered **UUIDv7** generated by the application (`gaggle_db::connection::new_id()`).
- **Timestamps**: Always `INTEGER` representing Unix epoch time in milliseconds (`gaggle_db::connection::now_ms()`).
- **JSON Columns**: Stored as `TEXT` and **must** include `CHECK(json_valid(column))` (or `CHECK(column IS NULL OR json_valid(column))` when nullable).
- **Boolean Columns**: Stored as `INTEGER` (`0` or `1`) with `CHECK(column IN (0, 1))`.
- **Enum Columns**: Stored as `TEXT` with `CHECK(column IN (...))` matching the allowed values in `docs/ERD.md`.
- **Secrets / API Keys / OAuth Tokens**: Must never be stored in SQLite. Store only the keychain reference identifier in `secret_ref`.
- **Soft Deletes**: Use `archived_at` or `deleted_at` (`NULL` indicates active records).

## 2. Circular References & Specialized Indexes
- `messages.run_id` <-> `runs.trigger_message_id` and `chats.worktree_id` <-> `worktrees.chat_id` use `DEFERRABLE INITIALLY DEFERRED`.
- `tool_permissions` uses an expression index `UNIQUE(COALESCE(project_id, ''), extension_tool_id)` because standard SQLite `UNIQUE` treats `NULL` values as distinct.
- FTS5 virtual tables (`memories_fts` and `messages_fts`) are kept in sync via `AFTER INSERT`, `AFTER DELETE`, and `AFTER UPDATE` triggers.

## 3. Testing
- Use `gaggle_db::connect_in_memory().await?` in integration tests under `crates/gaggle-db/tests/`.
- Run `cargo test -p gaggle-db` to validate migrations and repository queries.
